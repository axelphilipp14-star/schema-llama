# AN-003 — Mesure E8 faussée deux fois (rechargement, puis détection de fin)

- **Date** : 2026-11-24 · **Phase** : C (M1)
- **Symptôme** : E8 mesuré à 45,6 s, puis 120,8 s (délai dépassé), puis 48,3 s sur 28 blocs, alors que la somme des durées prévues donne 30,1 s (16 blocs) et 43,3 s (28 blocs).
- **Trace** (`results/probe.mjs`, progression relevée chaque seconde) :
  1. 1re mesure : la page s'est figée à 12 s. Cause : j'avais modifié `src/store.ts` juste avant la mesure, le serveur Vite a rechargé la page pendant la lecture.
  2. 2e mesure : la fin n'était jamais détectée. **Vrai bug** : en fin de lecture, `Ticker` arrêtait l'animation sans synchroniser la progression du store (mise à jour limitée à 10 Hz) ; le bouton n'affichait jamais « ↺ Recommencer ».
  3. 28 blocs : l'animation finit bien à 43,3 s (progression 33,00 à 45 s), mais l'outil lisait le texte du bouton une fois par seconde, avec 2 requêtes par tour → détection en retard de 5 s.
- **5 pourquoi** (cause racine commune) : l'instrument de mesure n'avait pas été calibré sur un cas dont on connaît la réponse. → **Processus** : un test se calibre sur une référence connue avant d'être cru (règle §4 de la méthode).
- **Corrections** : synchronisation de la progression à la fin (`src/scene/Rig.tsx`) ; l'outil lit `window.__anim.progress` toutes les 100 ms (`scripts/measure-m1.mjs`) ; aucune modification du code pendant une mesure.
- **Vérification** : 16 blocs → 30,1 s mesurées pour 30,1 s calculées ; 28 blocs → 43,3 s pour 43,3 s.
- **Leçon** : comparer chaque mesure à sa valeur calculée ; un écart non expliqué se trace avant d'être publié, dans un sens comme dans l'autre.
